02 · THE IDEA

把它想成三次“翻译”。

每一层只做一件事，所以整条链路既容易理解，也方便在出故障时定位。

VPN

HarmonyOS：决定拦谁

VpnExtensionAbility 按白名单或黑名单接管 App。被接管的 IPv4 流量进入 TUN，未被接管的 App 继续走设备原网络。

USB

hdc：只负责搬运

Control 和 Data 都连接设备本机的 127.0.0.1:27183，再由 hdc rport 通过 USB 送到 Mac 的本地端口。

gV

Mac：把包变回连接

gVisor 在用户态接住原始 IP 包，把 TCP、UDP 和 DNS 变成 Mac 的普通 socket。于是流量自然沿着 Mac 已有的企业网络出站。

最关键的一点 Mac 不是把手机的原始 IP 包“塞进网卡”，而是替手机重新发起普通连接。

这就是它不需要 root、不创建 macOS utun、也不修改 pf 的原因。Mac 当前能访问的企业路由和 split DNS，会被这些普通连接自然复用。

✓
不自定义 USB 协议复用开发工具 hdc 的 rport 能力。
✓
不暴露局域网端口设备与 Mac listener 都只绑定 loopback。
✓
不修改 Mac 系统网络不创建 utun，不注入 pf，不需要 root。
✓
不让隧道套娃Control / Data socket 会先调用 protect()。
03 · ROUTING & PROXY

名单决定“谁进桥”，抓包决定“Mac 怎么代发”。

这是两个互不混淆的开关：App 分流发生在 HarmonyOS，mitmweb 分支发生在 Mac。

当前模式 App 与“已选名单”的关系 是否进入 USB Tunnel 系统配置
白名单 已选 App → 进入 trustedApplications
白名单 未选 App ↗ 设备直连 不被 VPN 接管
黑名单 已选 App ↗ 设备直连 blockedApplications
黑名单 未选 App → 进入 默认由 VPN 接管
任意模式 HarmonyNetBridge 自身 → 始终进入 隐式规则，名单里不显示

proxy 模式做了什么？

手机没有被设置成“全局 HTTP 代理”。进入 Tunnel 的流量先照常到达 gVisor，再由 relay 按协议选择分支。

TCP
80 / 443 / 8080 / 8443relay 用内部 HTTP CONNECT 接入受管 mitmweb。
UDP
443 / QUIC主动拒绝，促使支持回退的客户端改走 TCP。
DNS
企业 split DNS继续由 Mac resolver 处理，不送进 mitmweb。
HTTPS
解密需要用户确认 CA手机需安装并信任当前 mitmproxy CA；证书 pinning 仍可能拒绝。
04 · HNB/1

为什么要分成 Control 和 Data 两条连接？

控制消息很少但必须及时；IP packet 很多。分开之后，停止、心跳和状态不会被大流量堵住。

同一个会话，两条互不抢锁的 TCP 通道

Control 握手会生成一次性随机 session token；Data 必须用这个 token 绑定到仍在线的 Control 会话。两条连接各自维护顺序号和心跳。

05 · BOUNDARIES

它擅长什么，也明确不承诺什么。

这是面向真机开发调试的桥，不是面向消费者的 USB 网络共享产品。

当前只处理 IPv4支持 TCP、UDP、UDP/TCP DNS；IPv6、ICMP 和其他原始协议不在当前范围。
一次只服务一台设备依赖已授权的 USB 调试与 hdc；多设备时必须显式选择，不能静默操作全部设备。
HTTPS 解密有边界需要用户安装并信任 CA；证书 pinning、企业策略或禁用用户 CA 的 App 仍可能失败。
只能存在一个活动 VPN其他 VPN、企业设备策略或用户撤销授权，都可能阻止 Tunnel 创建或结束连接。
Mac DNS 是能力的一部分relay 复用 macOS resolver，并按域名后缀选择企业 split DNS，不偷偷回退公共 DNS。
静态构建不等于真机通过编译、单测和 HAP 打包能证明结构正确；真实分流、USB 生命周期与 CA 信任仍需真机检查。
为什么目标服务看到的是 Mac 的网络，而不是手机网络？

因为 gVisor 会在 Mac 用户态终止设备侧的 TCP/UDP 流，再用 Mac 的普通 socket 重新出站。目标服务面对的是 Mac 发起的连接，所以会沿用 Mac 当前的 Wi‑Fi、AnyConnect 与企业路由。

USB 只是传输线，为什么还需要 HNB/1 协议？

hdc 只负责把 TCP 字节搬过 USB。HNB/1 再给这些字节增加明确的消息类型、长度、顺序号和会话身份，让双方能安全区分控制命令、心跳与一个个完整 IP packet。

白名单为空时，会不会意外接管所有 App？

不会。当前实现把 HarmonyNetBridge 自身作为隐式白名单成员，因此空白名单时只有本应用进入 Tunnel；黑名单为空则表示不排除任何 App，所有 App 都会进入 Tunnel。
